## Q1. PagedAttention — KV cache 단편화와 페이징 해결

LLM 서빙 시스템에서 KV Cache의 메모리 단편화(memory fragmentation)가 발생합니다. 

(1) 기존 시스템이 KV Cache를 연속 메모리(contiguous memory)로 할당할 때 왜 단편화가 심하게 발생하는지 설명하세요. 

(2) vLLM이 도입한 PagedAttention은 이 문제를 OS의 가상 메모리 페이징(paging) 개념과 연결지어 어떻게 해결하나요? 

(3) Attention 연산 관점에서, 물리적으로 비연속(non-contiguous)인 메모리 블록에 흩어진 KV 토큰들에 대해 attention을 계산할 때 표준 attention 수식상 달라지는 점이 있는지 설명해보세요.

### Answer 1.

1. 왜 KV Cache 단편화가 발생하는가?

LLM은 auto-regressive하게 생성. 문제는 각 request마다 몇 개의 토큰을 생성할지를 미리 알 수 없다는 것이다.

기존 시스템은 요청당 "최대 시퀀스 길이"만큼 KV cache를 연속적인 블록으로 미리 예약해둔다. 실제 생성이 짧게 끝난다면, 그 이후가 통째로 낭비되고(internal fragmentation), 요청마다 길이가 달라서 남은 공간에 새 요청이 들어가지 않는 external fragmentation도 생겨 실험적으로 KV Cache의 60~80%가 낭비된다고 한다.

2. PagedAttention

PagedAttention은 OS paging 기술을 차용하여, KV cache를 고정 크기 블록(=page)로 쪼개 물리적으로 흩어져있는 메모리에 저장하고, page table을 통해 논리 주소 → 물리 주소 매핑을 수행한다.

필요할 때마다 블록을 하나씩 동적으로 할당받으므로 기존에 통째로 낭비되던 문제가 마지막 블록 일부의 문제로 제한된다. 즉, 미리 최대치를 잡지 않아도 되므로 낭비가 거의 없게 된다.

또한, 동일한 prefix를 공유하는 요청들은 같은 물리 블록을 공유 (copy-on-write) 할 수 있어 추가적인 절약이 가능하다.

3. 비연속적인 메모리 블록에서 Attention 수식이 달라지는가?

Attention 수식은 달라지지 않는다. K, V가 논리적으로 올바른 순서이기만 하면 되기 때문이다. PagedAttention은 커널이 Block table을 참조하여 흩어져 있는 물리 block을 올바른 순서로 모아서 K, V 행렬을 구성하게 된다. 즉, Attention 수식은 그대로 동작하고, 모으는 연산(gather)이 추가되므로 구현 복잡성만 높아지게 된다.

> **흔히 놓치는 지점:** (3)에서 "수식이 바뀐다"고 답하기 쉬운데, 수식은 불변이고 달라지는 건 커널 레벨의 메모리 접근(block table gather)이라는 점.
> **한 단계 더:** 대표 논문 vLLM/PagedAttention (Kwon et al., 2023). 블록 단위 매핑이 공통 prefix의 KV 공유(copy-on-write)를 가능케 한다는 점까지 언급하면 좋다.

## Q2. Continuous Batching이 throughput을 올리는 원리

Continuous Batching(=in-flight batching)이 무엇이고, 기존 static batching 대비 왜 GPU throughput을 크게 올리는지 설명해보세요.

### Answer 2.

기존의 Static batching은 하나의 배치 내 한 개의 요청이 끝나고 다른 요청이 모두 끝날 때까지 새로운 요청을 받지 못한다. 즉, 배치 안의 모든 요청이 끝날 때까지 기다렸다가 다음 배치를 처리하게 되므로, 짧은 시퀀스에 쓰이는 Padding 연산이 낭비가 된다.

Continuous Batching은 하나의 요청이 끝날 때마다 새로운 요청을 넣을 수 있어서 배치를 동적으로 재구성하게 된다. 특히, 요청 별 길이 분산이 클때 짧은 요청이 끝나는 순간 새로운 요청을 바로 투입함으로써 더 큰 효과를 얻는다.

Continuous Batching은 PagedAttention 덕분에 가능한데, 서로 다른 요청의 KV Cache 크기를 독립적으로 동적 조정할 수 있기 때문이다. 즉, 연속 메모리 방식이었다면 중간에 새로운 요청을 끼워 넣을 수 없는데, PagedAttention은 유연하게 메모리를 관리하므로 가능하다.

> **한 단계 더:** "vLLM이 왜 빠른가?"에는 PagedAttention + Continuous Batching 두 축을 묶어 답하면 좋다.

## Q3. Chunked Prefill과 Prefill-Decode interference

Continuous Batching에서 긴 프롬프트의 Prefill이 기존 요청들의 Decode를 방해하는 문제가 있습니다. 이 Prefill-Decode interference가 무엇이고, Chunked Prefill이 어떻게 완화하는지 설명해보세요.

- Prefill(프롬프트 전체를 한 번에 처리): 입력 토큰 수 $T_p$에 대해서 $O(T^2_p)$ Attention → compute-bound
- Decode(토큰 1개씩 생성): 매 step마다 토큰 1개 → memory-bound

### Answer 3.

Continuous Batching에서 신규 요청의 Prefill과 기존 요청의 Decode를 같은 배치에 넣으면, Prefill은 수백~수천 토큰을 한 번에 처리해 GPU를 오래 점유한다. 그 동안 Decode 요청들은 대기하게 되므로, 기존 요청의 토큰 간 간격(TBT)이 급증하게 되고 신규 요청의 첫 토큰까지의 시간(TTFT)도 길어진다. 즉, 긴 프롬프트 하나가 들어오면 Decode 중인 요청이 그 시간만큼 멈추는 것처럼 느껴진다.(=Prefill-Decode interference)

Chunked Prefill은 Prefill을 한 번에 처리하지 않고, 고정크기의 청크로 쪼개 여러 step에 나눠 처리하도록 합니다. 즉, 매 step 마다 $C$개의 Prefill 토큰 + $B$개의 Decode 토큰으로 배치를 구성한다. 

Prefill이 GPU를 독점하는 시간이 줄어 TBT 스파이크가 완화되고, Decode 요청이 매 step마다 꾸준히 진행되므로 latency가 안정화되며, 청크 크기로 TTFT와 TBT의 Trade-off를 조절 가능하다.

> **한 단계 더:** Sarathi-Serve, DeepSpeed-FastGen의 chunked prefill 구현을 언급하면 좋다.

## 오늘의 수식 카드

**KV Cache 메모리 크기**

$$\text{KV bytes} = 2 \times L \times n_{layers} \times n_{kv\_heads} \times d_{head} \times b_{precision}$$

**Chunked Prefill 배치 구성**

$$\text{batch} = \underbrace{C\ \text{Prefill 토큰}}_{\text{신규 요청 일부}} + \underbrace{B\ \text{Decode 토큰}}_{\text{기존 요청들}}$$

| 기호 | 의미 |
|------|------|
| $L$ | 시퀀스 길이 |
| $C$ | Prefill 청크 크기(예: 512) — TTFT↔TBT 조절 손잡이 |
| TTFT | 신규 요청의 첫 토큰까지 시간 |
| TBT | 기존 요청의 토큰 간 간격 |

직관: PagedAttention은 KV cache를 "안 낭비하게" 관리하고, Continuous Batching은 GPU를 "안 놀게" 채우며, Chunked Prefill은 긴 Prefill이 Decode를 "안 방해하게" 쪼갠다 — 세 축이 함께 vLLM류 서빙의 throughput을 만든다.
