## Q1. Fixed-size vs Semantic Chunking

RAG 파이프라인에서 **Chunking**은 문서를 검색 가능한 단위로 분할하는 과정입니다.

**다음 세 가지를 설명하세요:**

1. **Fixed-size Chunking** — 고정 크기(토큰/문자 수)로 문서를 자르는 방식의 장단점을 설명하세요.

2. **Semantic Chunking** — 의미적 경계(문장, 단락, 섹션)를 기반으로 분할하는 방식과, Fixed-size 대비 장점을 설명하세요.

3. **Chunk 크기의 Trade-off** — Chunk가 너무 작거나 클 때 각각 어떤 문제가 생기는지 검색 품질과 컨텍스트 완결성 관점에서 설명하세요.

### Answer 1.

1. Fixed-size Chunking은 문서 내 맥락과는 관계없이, 사전에 정해진 크기대로 청크를 생성하는 방법이다. 단순히 길이에 따라서 청크를 분할하면 되므로 간편하게 이루어지지만, 문맥을 전혀 고려하지 않으므로 의미적으로 연속된 문장이 청크 경계에서 끊기는 문제가 발생한다.

2. Semantic Chunking은 인접한 문장들의 임베딩 간 Cosine similarity를 측정해 유사도가 급격히 떨어지는 지점을 경계로 하여 청크를 분리하는 방식이다. Fixed-size 방식과 비교했을 때 의미적인 단절이 일어나지 않는다는 장점이 있다.

3. 청크가 너무 작다면 검색 시 노이즈가 많아져 Top-K 결과에 관련 없는 조각들이 섞일 가능성이 높아진다. 또한, 어휘 정보가 부족하므로 임베딩 품질 자체가 낮아지고 Query와의 의미적 매칭이 불안정해진다.

청크가 너무 크다면 하나의 청크 안에 의미적으로 구분되는 여러 파트가 존재하게 되어 검색 정확도 및 답변 생성에 악영향을 줄 수 있다. 특히 여러 의미가 섞이게 되면 임베딩이 평균화(Dilution)되어 특정 Query와의 유사도가 낮아지는 문제점이 존재한다.

## Q2. Overlap Chunking과 문제점

**Overlap Chunking**은 인접한 chunk 간에 일정 구간을 겹치게 분할하는 방법입니다.

**두 가지를 답하세요:**

1. 청크 오버랩이 무엇인지 설명하고, `chunk_size=100 tokens, chunk_overlap=20 tokens`일 때 청크들이 어떤 식으로 생성되는지 직관적으로 설명하세요. (예: 첫 번째 청크는 토큰 1~100, 두 번째 청크는 토큰 몇~몇?)

2. **Overlap의 부작용** — Overlap이 클수록 발생하는 문제(중복 검색, 인덱스 크기)를 설명하고, 적절한 overlap 비율을 설정하는 기준을 말해보세요.

### Answer 2.

1. 청크 오버랩은 서로 연속된 두 청크에 `chunk_overlap`크기 만큼 동일한 토큰을 포함한 개념이다. 이는 종이를 서로 겹쳐서 이어붙이는 것과 동일하게 볼 수 있다. `chunk_size=100 tokens, chunk_overlap=20 tokens` 조건에서는 첫번째 청크에 1~100 토큰이 포함된다면, 두번째 청크에는 81~180 토큰이 해당되게 된다.

2. Overlap이 클수록 서로 다른 두 청크에 같은 부분이 과하게 포함되어 서로의 임베딩이 비슷해지는 문제점이 생길 수 있다. 또한, 검색 시 Top-K에 사실상 동일한 내용의 청크가 중복으로 올라오게 되어 반복된 정보를 LLM에게 전달하는 문제가 생길 수 있다.

## Q3. Parent Document Retriever

**Parent Document Retriever**는 LangChain 등에서 구현된 계층적 청킹 전략입니다.

**두 가지를 답하세요:**

1. **Parent Document Retriever의 구조** — Child chunk로 검색하고 Parent chunk를 반환하는 방식을 설명하고, 왜 이 구조가 필요한지 설명하세요.

```
문서
└── Parent chunk (큰 단위, LLM에 전달)
    ├── Child chunk 1 (작은 단위, 검색용)
    ├── Child chunk 2
    └── Child chunk 3
```

2. **이 방식의 장점** — Precision, Recall과 LLM 컨텍스트 품질 간의 trade-off를 어떻게 해결하는지 설명하세요.

### Answer 3.

1. 벡터 검색의 정확도는 청크가 작을수록 유리하지만, LLM이 답변을 생성할 때는 문맥이 풍부한 덩어리가 더 유리하다. 이러한 특징을 반영하기 위해서, Parent Document Retriever는 전체 문저를 두 단계로 chunking하여 Parent Chunk(큰 단위), Child Chunk(작은 단위)로 나누게 된다. 이때, Child Chunk는 더 구체적인 정보를 담고있으므로 Retrieval에 사용되고, 검색된 Child Chunk의 Parent Chunk를 LLM에 문맥으로 전달하게 된다.

2. Child chunk를 이용한 검색은 의미적 집중을 통해서 관련 청크를 정밀하게 찾고자 하는 방식이다. 이러한 방식은 Precision을 높일 수 있다. 반면, LLM에게는 Parent chunk가 입력되는데, 이때 주변 문맥까지 포함되므로 답변에 필요한 정보 누락이 줄어들게 되어 Recall이 증가하는 효과를 동시에 가지게 된다.
